# 적용 단계: 프로젝트에 맞게 고쳐 하네스에 넣기

외부 스킬을 **그대로 깔지 않고**, 이 프로젝트의 규칙과 도구에 맞게 고쳐서 하네스의 알맞은 자리에 넣는다. 원본과 무엇이 달라졌는지 남기고, 넣은 뒤 실제로 불리고 도는지 확인한다.

## 0. 시작 조건

다음이 모두 있어야 시작한다. 없으면 SKILL.md의 1~5단계(찾기와 판정)를 먼저 한다.

- 대상 스킬의 저장소, 스킬 폴더 경로, **검사한 커밋 SHA**
- 보안 판정과 근거, 적합성 판정과 "고칠 곳"
- 사용자가 이 스킬을 쓰겠다고 한 말

시작하지 않는 경우:

- 보안 판정이 "위험"이다. 고쳐서 쓰자는 요청이어도 원본을 들이지 않는다. 필요한 방법만 뽑아 새로 쓰는 것을 제안한다.
- 라이선스가 없거나 수정과 재배포를 허락하는지 알 수 없다. 원문을 옮기지 않고, 방법만 참고해 새로 쓴다. 이 경우에도 참고한 출처는 적는다.
- 감별한 뒤 시간이 지났다. 검사한 SHA 뒤로 스킬 폴더에 커밋이 있으면 그 차이를 다시 점검한다.

```bash
gh api "repos/<소유자>/<저장소>/compare/<검사한 SHA>...<기본 브랜치>" --jq '.files[] | select(.filename | startswith("<스킬 폴더>")) | .filename'
```

## 1. 이 프로젝트의 하네스 읽기

고치기 전에 "어디에 무엇이 있는지"를 실제로 읽는다. 대화에 이미 있으면 다시 읽지 않는다.

| 볼 것 | 왜 |
| --- | --- |
| 작업 지침(AGENTS.md)과 그것이 가리키는 문서 | 스킬이 따라야 할 규칙. 부딪히면 프로젝트 쪽이 이긴다 |
| 프로젝트 `.agents/skills`와 개인 `~/.agents/skills`, `~/.codex/`(config.toml, AGENTS.md) | 이미 있는 스킬, 에이전트와 겹치는지, 어디에 둘지 |
| 실행 명령(package.json scripts, 빌드와 테스트 명령) | 스킬 속 명령을 무엇으로 바꿀지 |
| 스택과 버전, 폴더 구조 | 경로와 예시 코드를 무엇으로 바꿀지 |
| 사용자의 개인 지침과 점검표 | 사용자가 이미 정한 선호와 금지 |
| 운영체제와 셸 | 스크립트가 여기서 도는지 |

## 2. 어떤 모양으로 넣을지 정하기

"하네스에 적용"이 꼭 새 스킬 하나를 뜻하지는 않는다. **가장 작은 모양**을 고른다.

| 원본이 주는 것 | 넣는 모양 |
| --- | --- |
| 한 종류의 일을 처음부터 끝까지 하는 절차 | 새 스킬 |
| 이미 있는 에이전트가 하는 일의 더 나은 방법 몇 가지 | 그 일을 정한 지침(AGENTS.md나 하위 폴더의 지침)에 몇 줄 더하기를 제안(새 스킬을 만들지 않는다) |
| 하지 말아야 할 것, 확인할 것의 목록 | 기존 점검표에 항목 더하기 |
| 쓸 만한 스크립트 하나 | 프로젝트 스크립트로 옮기고 스킬은 그것을 부르기만 함 |
| 이미 있는 것과 대부분 겹침 | 넣지 않는다. 다른 점만 기존 것에 반영 |

둘 곳:

- **개인(`~/.agents/skills`)**: 나만 쓴다. 저장소를 건드리지 않는다. 정하지 않았으면 이쪽이 기본이다.
- **프로젝트(`.agents/skills`)**: 팀 전원에게 적용되는 저장소 변경이다. 프로젝트의 브랜치, PR, 리뷰 규칙을 그대로 따른다. 작업 지침 파일(AGENTS.md)을 고쳐야 연결되는 경우에는 그 파일의 변경 규칙이 따로 있는지 확인하고, 그 변경은 스킬을 넣는 일과 나눠서 제안한다.

## 3. 고칠 계획 세우기

원본을 SHA에 고정해 받아 읽고(복제하지 않는다), 아래 표를 채운다.

```bash
gh api "repos/<소유자>/<저장소>/contents/<파일 경로>?ref=<SHA>" --jq .content | base64 -d
```

| 고치는 종류 | 하는 일 |
| --- | --- |
| 경로와 이름 | 원본 저장소의 경로, 패키지 이름, 내부 문서 링크를 이 프로젝트의 것으로 바꾼다. 대응하는 것이 없으면 그 단락을 뺀다 |
| 명령 | 패키지 관리자와 실행 명령을 프로젝트의 것으로 바꾼다(예: `pnpm --filter x storybook` → `npm run storybook`). 프로젝트에 없는 명령은 지어내지 않는다 |
| 버전 | 스킬이 전제하는 버전과 프로젝트 버전이 다르면, 그 버전에서 되는 방법으로 고치거나 그 부분을 뺀다. 스킬을 넣으려고 프로젝트의 의존성을 올리지 않는다. 올려야만 쓸 수 있으면 멈추고 사용자에게 알린다 |
| 규칙 충돌 | 프로젝트 규칙과 부딪히는 문장은 프로젝트 쪽으로 고친다. 양쪽 문장을 계획에 나란히 적는다 |
| 권한과 승인 | 승인 범위를 넓히는 문장("~을 승인으로 간주", "막히면 권한을 올려라"), 자동 커밋, 자동 머지, 자동 설치를 뺀다. 필요하면 "사용자에게 묻는다"로 바꾼다 |
| 본문 밖의 지시 | "이 명령의 출력을 따르라"는 구조면, 그 명령을 사용자 승인 아래 한 번 돌려 출력을 읽고 점검한 뒤 쓸지 정한다. 읽지 못한 지시를 따르는 스킬은 넣지 않는다 |
| 스크립트 | 이 운영체제와 셸에서 도는지 본다. 고칠 수 없으면 뺀다. 내려받아 실행하는 부분은 뺀다 |
| 언어와 문체 | 사용자가 쓰는 언어로 옮기고, 프로젝트와 사용자의 문서 작성 규칙을 따른다 |
| 겹치는 부분 | 기존 스킬이나 에이전트가 이미 하는 일은 빼고 그것을 가리킨다 |
| 불릴 조건 | frontmatter의 `description`을 이 프로젝트에서 실제로 쓰는 말로 다시 쓴다. 기존 스킬과 같은 말에 함께 불리지 않게 한다 |
| 길이 | 이 프로젝트에 해당 없는 예시와 일반론을 덜어 낸다. 매번 문맥에 실리는 글이다 |

고치고 나서 원본의 뜻이 절반도 남지 않으면 "원본을 고친 것"이 아니라 "참고해 새로 쓴 것"이다. 그렇게 적는다.

## 4. 사용자에게 계획 보이고 승인받기

쓰기 전에 보인다. 이 승인 없이 파일을 만들지 않는다.

- 넣는 모양과 둘 곳, 그렇게 고른 이유 한 줄
- 3단계 표에서 실제로 고치는 것: "원본 → 고친 것"으로 줄마다
- 뺀 것과 이유
- 프로젝트 규칙과 부딪혀 프로젝트 쪽으로 고친 곳(양쪽 문장)
- 고쳐도 남는 한계(예: "스토리 2개뿐이라 당장 불릴 일이 적다")

"이대로 넣기, 고칠 곳 더 있음, 넣지 않기" 가운데 무엇으로 할지 글로 묻고 답을 기다린다.

## 5. 쓰기

- 승인받은 위치에 승인받은 내용만 쓴다. 다른 파일을 정리하거나 고치지 않는다.
- 기존 파일(지침, 점검표)에 더하는 경우에는 더하는 줄만 넣고 나머지는 건드리지 않는다. 다른 사람이 만든 파일이면 넣기 전에 한 번 더 확인한다.
- 새 스킬 폴더에는 `SOURCE.md`를 함께 둔다.

```markdown
# 출처

- 원본: <소유자>/<저장소>, <스킬 폴더 경로>
- 검사하고 가져온 커밋: <전체 SHA>
- 라이선스: <SPDX 표기>
- 가져온 날: <YYYY-MM-DD>
- 감별 결과: 보안 <판정>, 적합성 <판정>

## 원본에서 바꾼 것

- <고친 종류>: <원본> → <고친 것>
- 뺀 것: <무엇을, 왜>
```

- 라이선스가 저작권 표시를 요구하면(MIT 등) 원본의 표시를 `SOURCE.md`에 옮긴다.
- 프로젝트에 두는 경우 커밋, 브랜치, PR은 프로젝트 규칙과 사용자의 지시를 따른다. 지시 없이 커밋하거나 PR을 열지 않는다.

## 6. 하네스에 연결하기

파일을 두는 것만으로 쓰이지는 않는다. 누가 언제 부르는지를 정한다.

- **스스로 불리게**: `description`의 말이 실제 요청과 맞는지 본다. 이것으로 충분하면 여기서 끝낸다.
- **에이전트가 쓰게**: 구현자나 리뷰어 에이전트가 이 스킬을 써야 하면, 그 일을 정한 지침이나 위임 브리프에 한 줄을 더한다. 어느 에이전트의 어느 단계인지 사용자에게 보이고 넣는다.
- **평가에 쓰게**: 채점이나 리뷰에 쓰는 스킬이면, 구현 때 쓰는 스킬과 겹치지 않는지 본다. 만든 쪽과 채점하는 쪽이 같은 기준을 쓰면 자기 채점이 된다.
- 연결한 곳을 `SOURCE.md` 끝에 적는다. 나중에 뺄 때 찾을 수 있게 한다.

## 7. 확인

넣었다고 끝내지 않는다. 다음을 실제로 해 보고, 한 것과 못 한 것을 나눠 보고한다.

- **불리는가**: 스킬 목록에 잡히는지 본다. 새 세션에서만 잡히는 환경이면 그렇게 알린다.
- **도는가**: 이 프로젝트의 작은 실제 일 하나에 써 본다(예: 컴포넌트 하나의 스토리 쓰기). 스킬 속 명령이 모두 실행되는지, 가리키는 경로가 모두 있는지 본다.
- **규칙을 지키는가**: 결과물이 프로젝트의 형식 검사, 빌드, 관련 테스트를 통과하는지 본다. 시험으로 만든 결과물은 사용자가 원하지 않으면 지운다.
- **겹쳐 불리지 않는가**: 비슷한 기존 스킬과 같은 요청에 둘 다 불리면 `description`을 고친다.

실패하면 고치고 다시 확인한다. 두 번 고쳐도 안 되면 넣은 것을 빼고 이유를 보고한다.

## 8. 보고

- 무엇을 어디에 넣었는가(파일 경로)
- 원본에서 바꾼 것 요약
- 어디에 연결했는가
- 확인한 것과 결과, 확인하지 못한 것
- 빼는 법: 지울 파일과 되돌릴 줄
- 갱신하는 법: 원본이 바뀌면 `SOURCE.md`의 SHA부터 차이를 다시 점검한다는 것
